# 04 · pi (pi-mono) 深度研究：模型运行、调度、工具调用与上下文管理

> 研究对象：`badlogic/pi-mono` / `earendil-works/pi`，MIT，TypeScript monorepo
> 本文聚焦四层：pi-ai（模型接入）→ pi-agent-core（运行时）→ coding-agent（会话/上下文）→ 工具系统。

---

## 1. 总体分层（各包边界极清晰）

```
用户 / Web UI / Slack / RPC 上层入口
        │
┌───────▼────────────┐
│ pi-coding-agent     │ 产品层：CLI/TUI、会话持久化、skills、扩展、compaction
├─────────────────────┤
│ pi-agent-core       │ 运行层：Agent 状态机、agent-loop、工具调度、steering
├─────────────────────┤
│ pi-ai               │ 模型层：统一多 Provider 流式 API、消息协议、成本计算
└─────────────────────┘
        │
OpenAI Responses/Completions · Anthropic Messages · Google GenAI/Vertex ·
Bedrock · Mistral · Ollama · Azure · Codex …（15+ providers）
```

设计哲学：**"RL 训练出来的前沿模型只需要薄脚手架"**——系统提示词 <1000 token（可低至 ~200），核心只有 4 个工具（read/write/edit/bash），其余全靠扩展。上下文窗口才是真正的瓶颈，框架开销大多适得其反。

## 2. 模型运行与调度（pi-ai）

### 2.1 统一消息协议（types.ts，全层词汇表）
- 三类消息：`UserMessage` / `AssistantMessage` / `ToolResultMessage`。
- Assistant 内容块：`text` / `thinking` / `toolCall`。
- **统一流式事件契约**（所有 provider 归一为同一形状）：
```
start
text:      text_start → text_delta* → text_end
thinking:  thinking_start → thinking_delta* → thinking_end
toolcall:  toolcall_start → toolcall_delta* → toolcall_end
done(reason: stop | length | toolUse)   或   error(aborted | error)
```
- 保证：终事件（done/error）解析出最终 result；事件按推送顺序立即投递，不合并不节流。

### 2.2 Provider 适配（关键文件与机制）
- `streamSimple(model, context, options)` → 按 `model.api` 查 api-registry → provider 实现做"原生事件 → 统一事件"翻译。
- 各家翻译要点：
  - **Anthropic**：`content_block_start/delta/stop` 映射到 text/thinking/toolcall 三元组；`input_json_delta` → toolcall_delta（累积 partialJson）；signature_delta 只更新 thinkingSignature 不发事件。
  - **OpenAI Responses 族**（含 Codex/Azure）：reasoning summary/raw reasoning 都归一为 thinking_delta；tool call ID 归一为 `call_id|item_id`；自研 SSE 传输替代官方 SDK。
  - **Google**：按 `isThinkingPart` 区分 thinking/text；functionCall 是结构化对象 → 一次合成 toolcall_delta，不需要 partial JSON 解析器。
- **部分 JSON 解析与恢复**（各家共用的精华）：工具参数流式累积 partialJson，用 `parseStreamingJsonThrottled()`——**新增 ≥256 字节才重解析**，把流中解析成本从二次方压到线性；解析失败用自家 RelaxedJson 修复式解析器兜底；`toolcall_end` 时无条件做最终权威解析。**畸形/截断的参数增量不会让流崩掉**，后续合法增量可恢复结构化参数。
- **停止原因与错误两阶段语义**：模型语义（end_turn/tool_use/max_tokens）与传输失败（网络/解析/abort）分开；provider wrapper 捕获异常 → 终态 error 事件（abort 信号置位时归为 aborted），并附 HTTP 错误体/原始请求 dump。
- **取消分层**：AI 请求 signal → wrapper 终态 → agent-loop 每个事件前检查 signal（可用最近 partial 合成 aborted 消息）→ 会话级 abort。工具执行的取消与模型流的取消分开（steering 中断可中止剩余工具但保留已完成结果）。
- 模型元数据：`models.generated.ts` 自动生成价格表，`calculateCost(model, usage)` 直接算钱；`ModelRegistry` 叠加自定义模型与鉴权状态。
- **中途换模型**：`prepareNextTurn` 钩子在每轮结束返回新的 context 快照 + 新 model + 新 thinking level——"便宜模型探索、强模型拍板"的调度策略无需在 loop 外再包一层。

### 2.3 调度入口
- `streamSimple()` 通用选项：apiKey、temperature、maxTokens、reasoning/thinkingBudgets、sessionId、**cacheRetention**、headers、signal。
- 两层接口：`stream()`（面向 provider 特定参数）/ `streamSimple()`（面向应用层，agent 默认用它）。

## 3. Agent Loop（pi-agent-core）：双 while(true) 状态机

### 3.1 结构（`packages/agent/src/agent-loop.ts`，runLoop ~400 行）
```
agentLoop(prompts, context, config, signal, streamFn) → EventStream
  └ runLoop()：外层 while(true)
      ├ 内层 while：工具调用 + steering
      │    emit(turn_start)
      │    flush pendingMessages（steering 插话）进 context
      │    streamAssistantResponse()   ← 消费 pi-ai 统一事件流
      │    stopReason ∈ {error, aborted}? → turn_end → agent_end → return
      │    toolCalls 非空? → executeToolCalls()（并行/顺序）
      │    emit(turn_end, message, toolResults)
      │    prepareNextTurn()            ← 可换模型/换上下文/触发 compaction
      │    shouldStopAfterTurn()?       ← 可插拔终止条件
      └ followUpMessages 非空? → 作为新 pendingMessages continue
```
- **Enter = steering**（当前工具执行完、下次模型调用前注入）；**Alt+Enter = follow-up**（agent 本来要停时追加）。
- `agentLoopContinue()`：不从新 prompt 启动，直接续跑既有 context（重试场景——工具结果已在上下文里）。
- **EventStream 包装**：把异步事件流变成 `for await` 可迭代，`agent_end` 为终止事件并携带最终 messages。
- 为什么是显式状态机而不是递归？——长任务/频繁工具调用下递归调用栈不可控；状态机才能做到中途中断、恢复、插话。

### 3.2 工具执行调度（`executeToolCalls`）
- 判定规则：**这批工具调用里只要有一个声明 `executionMode: "sequential"`，整批退化为顺序执行**——不存在部分并行的中间态。
- 内置 7 工具（read/write/edit/bash/grep/find/ls）**全部默认并行**：bash 每次独立 shell 进程无共享状态；cd 后跑相对路径这类需求模型会分多轮调用而不是一次塞多条。
- sequential 模式是留给第三方扩展的：有状态副作用的工具（如数据库连接池）自行声明。
- **edit 的一致性来自互斥队列而非乐观锁**：`withFileMutationQueue(absolutePath, ...)` 按文件路径排队——"飞机洗手间"模式：同一文件同一时刻只进一个编辑。
- 钩子：`beforeToolCall` / `afterToolCall` 包裹每次执行；工具执行期间发 `tool_execution_start/update/end` 事件。
- 流式编辑守卫（AgentSession）：检查 toolcall_delta 里 edit 调用的参数，可提前 abort——**在工具还没跑完前就发现错误**。

### 3.3 消息状态管理
- agent-loop 内部始终用 `AgentMessage[]`，只在调 LLM 的边界才 `convertToLlm()` 转成 pi-ai 的 `Message[]`——**内部事实与传输格式解耦**。
- `transformContext` 钩子：每次模型调用前可变换 `AgentMessage[]`（扩展可做 RAG、历史过滤、记忆注入）。

## 4. 上下文管理（pi-coding-agent 的精华）

### 4.1 会话 = append-only 树（DAG）
- 每条 entry 有唯一 id + parentId，存 `.jsonl`。`/tree` 任意回溯、分支；所有分支共存在一个文件里。
- 换分支时**分支摘要（branch summarization）**：找新旧位置的最深公共祖先 → 收集被放弃分支的 entries → 预算内（最新优先）生成结构化摘要 → 在导航点写入 BranchSummaryEntry，注入新分支。

### 4.2 Compaction（自动压缩）
- 触发：`contextTokens > contextWindow - reserveTokens`（默认 reserve 16,384；`/compact` 可手动带聚焦指令）。
- 流程：从最新往回累计 token 到 `keepRecentTokens`（默认 20k）找切点 → 摘要旧行为 → 写入 CompactionEntry（带 firstKeptEntryId）→ 模型看到 = system prompt + 摘要 + 从切点保留的消息。
- **切点规则**：只能切在 user/assistant/bash/custom 消息；**绝不切在 tool result**（必须与 tool call 在一起）。
- **分裂轮（split turn）**：单轮超预算时切点落在轮中间 → 生成两份摘要（历史摘要 + 轮前缀摘要）合并。
- **累计文件追踪**：每次摘要提取"读过/改过哪些文件"，跨多次 compaction 累计——摘要永远带着文件操作清单。
- **摘要格式是结构化模板**（这是最值得抄的部分）：
```
## Goal / ## Constraints & Preferences / ## Progress（Done/In Progress/Blocked）
## Key Decisions（决策+理由）/ ## Next Steps / ## Critical Context
read-files: [...]  modified-files: [...]
```
- 序列化协议防"摘要被当对话续写"：`[User]: … [Assistant thinking]: … [Assistant tool calls]: read(...) [Tool result]: …`。
- 扩展可完全接管：`session_before_compact` / `session_before_tree` 事件可取消或提供自定义摘要（用别的模型、自定义格式）。

### 4.3 渐进披露（Progressive Disclosure）
- **Skills**：能力包 = 指令 + 工具，只在触发词匹配时加载，不预先塞上下文——**保护 prompt cache 前缀稳定**。
- AGENTS.md（项目指令）+ SYSTEM.md（替换/追加系统提示词）+ prompt templates（`/name` 展开 Markdown 模板）。
- **pi 故意不做 MCP**：作者的理由是一个 MCP server 可能给上下文加 13,700+ token——上下文预算优先。要 MCP？写个扩展加。
- 扩展 20+ 生命周期钩子：改写即将发给模型的消息、拦截工具调用、注入 turn 前消息（RAG/记忆）、注册工具/命令/快捷键、把状态持久进会话。运行时 TS 编译免预编译加载，社区 2000+ 包。

### 4.4 会话级行为（AgentSession）
- 订阅 agent 事件 → 持久化消息（message_end 时写盘）→ 驱动扩展钩子 → 自动重试（按 stopReason=error + errorMessage 启发式）→ TTSR（流式响应处理）→ streaming-edit abort 检查。
- Durable 变体（pi-durable）：checkpoint 会话、模型调用与工具执行，进程崩溃后可恢复。

## 5. 与 dsh 的对照（取长补短表）

| 维度 | pi | dsh | 自研怎么取 |
|---|---|---|---|
| 内核 | 无容器，直接模块分层 | Cordis IoC 容器 | 用 dsh/cordis 拿容器，抄 pi 的分层边界 |
| 模型层 | pi-ai 统一流式契约 + 部分 JSON 恢复 | llm 接缝 + 3 协议适配 | **直接依赖 pi-ai 或抄它的统一事件契约与 256B 节流解析** |
| 主循环 | 双 while + steering/follow-up + prepareNextTurn | turn/step + waterfall 管线 + PreparedStep 冻结 | loop 语义抄 pi（简单可控），拦截面用 dsh 事件域 |
| 工具 | 4-7 个极简工具 + 按路径互斥队列 | 作用域注册表 + 三段管线 + 沙箱审批 | 执行管线用 dsh（有权限门），edit 互斥队列抄 pi |
| 上下文 | DAG 会话 + 结构化 compaction + 渐进披露 | append-only 日志 + Projection + compaction 插件 | 事实层用 dsh 事件流，**摘要模板与切点规则抄 pi** |
| 安全 | 无内置（交容器） | 沙箱 + 审批 + permission preset | 用 dsh 的 |

## 6. 自研落地建议（pi 部分）

1. **直接复用 pi-ai 包**（MIT）当模型层：省掉 15+ provider 适配，白拿流式契约、部分 JSON 恢复、成本计算。dsh 的 llm 接缝里写一个 pi-ai 桥接 provider 即可两全。
2. **compaction 摘要模板 + 切点规则 + 累计文件追踪**整套搬过来，替换/增强 dsh 的 compaction 插件配置。
3. **steering/follow-up 双插话机制**：你的产品要"会话式对话"，插话体验是关键手感，pi 的实现最干净。
4. **skill 渐进披露**保护缓存命中：默认会话不加载任何 skill，匹配触发才进上下文——与你"选对话不扫盘"的诉求完全一致。
